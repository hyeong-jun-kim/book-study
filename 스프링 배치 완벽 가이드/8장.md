## 8장: ItemProcessor

스프링 배치의 핵심 처리 흐름은 **읽기(Read)-처리(Processor)-쓰기(Write)**의 3단계로 이루어진다.

오늘 다룰 `ItemProcessor`는 스프링 배치 내에서 입력 데이터를 이용해 어떤 작업을 수행하는 컴포넌트이다.  
단순히 데이터를 넘기는 관문이 아니라, **배치의 비즈니스 로직이 구현되는 실질적인 작업 공간**이다.

스프링 배치는 이 `처리` 단계를 의도적으로 분리함으로써, `관심사의 분리`라는 중요한 설계 원칙을 지킨다.

`ItemReader`는 '어떻게 데이터를 가져올 것인가'에만 집중하고, `ItemWriter`는 '어떻게 데이터를 쓸 것인가'에만 집중한다. 그리고 `ItemProcessor`는 가져온 데이터를 어떻게 비즈니스 규칙에 맞게 가공할 것인가에만 집중하게 된다.

ItemProcessor의 인터페이스는 의도적으로 매우 단순하게 설계되었다. `process`라는 단 하나의 메소드만 가지고있다.

```java
package org.springframework.batch.item;

public interface ItemProcessor<I, O> {
    O process (I item) throws Exception; [cite: 40]
}
```

- <I, O> 제네릭: 입력과 출력의 타입이 같을 필요가 없다는 점이 중요하다.  
  ItemReader가 읽어온 객체를 ItemWriter가 필요로 하는 다른 타입의 객체로 변환하여 반환할 수 있다.
- `null` 반환의 의미: `process` 메소드가 `null`을 반환하면, 해당 아이템은 필터링되어 이후의 처리 과정으로 전달되지 않는다. 이는, `ItemReader`가 `null`을 반환하여 입력의 끝을 알리는 것과는 다른 동작이다.
- `throws Exception`: process 메소드는 Checked Exception을 포함한 모든 예외를 던질 수 있도록 설계되었다. 이는 아이템 처리 중 발생하는 비즈니스 예외를 잡의 실패, 건너뛰기(Skip), 또는 재시도(Retry) 정책과 연계하여 유연하게 처리할 수 있도록 하기 위함이다.
- **멱등성**: 내결함성을 위해 청크 단위 작업이 실패하면 해당 청크는 재시도될 수 있다. 이때, `ItemProcessor`는 동일한 아이템으로 여러 번 호출될 수 있으므로, 여러 번 실행해도 결과가 동일하게 유지되도록 멱등성을 갖게 설계해야한다.

스프링 배치는 자주 사용되는 패턴들을 위해 강력한 `ItemProcessor` 구현체들을 제공한다.

## ItemProcessor 구현체

### 1) `ValidatingItemProcessor`

데이터 처리의 첫 단계에서 데이터의 정합성을 보장하는건 매우 중요하다.

- 왜 Reader가 아닌 Processor에서 검증해야하는가?
  - ItemReader의 책임은 오직 **데이터를 읽어 객체로 만드는 것**이다. 여기에 비즈니스 검증 로직까지 들어가면 책임이 무거워진다.
  - ItemProcessor에서 검증을 담당하면, 어떤 종류의 ItemReader를 사용하든 일관된 검증 로직을 적용할 수 있다.
- `BeanValidatingItemProcessor` 활용
  - JSR-303 애너테이션을 사용하는 이 구현체는 편리하고 선언적인 검증을 가능하게 한다.
    spring-boot-starter-validation 의존성을 추가하면 바로 사용할 수 있다.

```java
@Bean
public BeanValidatingItemProcessor<Customer> customerValidatingItemProcessor() {
    // 이 프로세서는 Customer 객체의 애너테이션을 보고 자동으로 유효성을 검사한다.
    return new BeanValidatingItemProcessor<>();
}
```

- **유효성 검증 실패 시 처리 전략**
  - **기본 동작**: 예외 발생 대신, 검증에 실패한 아이템을 조용히 필터링하고 싶을 때는 setFilter(true) 옵션을 사용할 수 있다.
  - 이렇게 하면, 검증 실패 시 null을 반환하여 해당 아이템만 처리에서 제외하고 잡은 계속 진행한다.
- **커스텀 Validator 구현 심화**
  - **상태를 가지는 Validator**: `UniqueLastNameValidator` 예제처럼 중복 체크 등을 위해 이전 아이템의 처리 결과를 기억해야 하는 경우, `ItemStreamSupport`를 상속하여 `ExecutionContext`에 상태를 저장하고 복원할 수 있다.
  - **참고사항**: 코어 스프링 프레임워크의 `Validator`와 스프링 배치의 `Validator`는 서로 다른 인터페이스이다. 만약 코어 스프링의 `Validator`는 서로 다른 인터페이스이다. 만약 코어 스프링의 `Validator` 구현체를 배치에서 사용하고 싶다면, 스프링 배치가 제공하는 SpringValidator라는 어댑터 클래스로 감싸서 사용할 수 있다.

### 2) `ItemProcessorAdapter`

기존에 잘 만들어진 서비스 로직을 배치 잡을 위해 다시 개발하는 것은 비효율적이다.

ItemProcessorAdapter는 기존 `서비스 클래스`를 ItemProcessor로 변환해주는 다리 역할을 한다.

기존 서비스 클래스(UpperCaseNameService)

```java
@Service
public class UpperCaseNameService {
    public Customer upperCase(Customer customer) {
        Customer newCustomer = new Customer(customer);
        newCustomer.setFirstName(newCustomer.getFirstName().toUpperCase());
        // ...
        return newCustomer;
    }
}
```

어댑터 구성(Configuration)

```java
@Bean
public ItemProcessorAdapter<Customer, Customer> itemProcessor(UpperCaseNameService service) {
    ItemProcessorAdapter<Customer, Customer> adapter = new ItemProcessorAdapter<>();
    adapter.setTargetObject(service); // 호출할 대상 객체를 지정한다
    adapter.setTargetMethod("upperCase"); // 대상 객체에서 호출할 메소드 이름을 지정한다.
    return adapter;
}
```

### 3) `ScriptItemProcessor`

자바 클래스를 작성하고 컴파일 하는 대신, JavaScript, Groovy 등의 외부 스크립트 파일을 `ItemProcessor`로 사용하게 해주는 기능이다.

- **장점**: 잡의 로직이 자주 변경될 때, 자바 코드를 재배포하지 않고 스크립트 파일만 수정하여 대응할 수 있는 유연성을 제공한다.
- **동작**: 스프링 배치는 스크립트를 실행할 때, 처리할 아이템을 기본적으로 `item`이라는 이름의 변수에 바인딩하여 전달한다.
- 코드예시(upperCase.js)

```javascript
item.setFirstName(item.getFirstName().toUpperCase());
item.setMiddleInitial(item.getMiddleInitial().toUpperCase());
item.setLastName(item.getLastName().toUpperCase());
item;
```

### 4) `CompositeItemProcessor`

하나의 아이템에 대해 여러 단계의 처리를 순차적으로 적용해야 할 때, `CompositeItemProcessor`는 여러 `ItemProcessor`를 파이프라인처럼 연결하여 코드를 모듈화한다.

- 각 `ItemProcessor`가 단일 책임 원칙을 지키도록 도와준다. 로직을 각각 별도의 `ItemProcessor`로 분리하여 재사용성과 테스트 용이성을 극대화 시킬 수 있다.
- 구성: `setDelegates` 메소드에 처리 순서대로 `ItemProcessor` 목록을 전달한다.

```java
@Bean
public CompositeItemProcessor<Customer, Customer> itemProcessor() {
    CompositeItemProcessor<Customer, Customer> itemProcessor = new CompositeItemProcessor<>();
    itemProcessor.setDelegates(Arrays.asList(
        validator(),      // 1단계: 유효성 검사
        upperCaser(),     // 2단계: 대문자 변환
        lowerCaser()      // 3단계: 소문자 변환
    ));
    return itemProcessor;
}
```

### 5) `ClassifierCompositeItemProcessor`

`process` 메소드 내부의 복잡한 `if/else` 분기문을 외부로 분리하는 전략 패턴을 적용할 수 있게한다.

`Classifier`가 아이템의 내용을 보고 실행할 `ItemProcessor`를 동적으로 결정한다.

- 구성: Classifier 구현체를 만들어 `setClassifier` 메소드를 통해 주입한다.  
  `classify` 메소드는 아이템을 받아 `ItemProcessor`를 반환하도록 구현해야한다.

## Custom `ItemProcessor` 구현

대부분의 비즈니스 로직은 프로젝트에 고유하기 때문에, `ItemProcessor` 인터페이스를 직접 구현하는 경우가 흔하다.

구현 예시: 짝수 우편번호 필터링

```java
public class EvenFilteringItemProcessor implements ItemProcessor<Customer, Customer> {
    @Override
    public Customer process(Customer item) throws Exception {
        // 우편번호가 짝수이면 null을 반환하여 필터링한다.
        return Integer.parseInt(item.getZip()) % 2 == 0 ? null : item;
    }
}
```

결과 확인: `JobRepository`  
필터링된 아이템의 개수는 `BATCH_STEP_EXECUTION` 테이블의 `filter_count` 컬럼에 기록된다. 이를 통해 잡 처리 현황을 정확하게 파악할 수 있다.
